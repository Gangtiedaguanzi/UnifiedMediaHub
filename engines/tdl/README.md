From UnifiedMediaHub, run `pwsh -NoProfile -File scripts/build-tdl.ps1` using the verified portable Go 1.27.3 already in `.tooling/go`. Add `-Publish` to back up and replace only this application's runtime engine after tests and smoke checks. The script verifies the upstream archive, recreates only the exact `.cache/tdl-build/tdl-0.20.4` tree after checking its ancestors and descendants for reparse points, applies the reviewed `overlay/`, verifies dependency checksums, tests affected packages, and builds Windows amd64 with CGO disabled. Existing upstream/toolchain/module/build caches are reused. No global Go configuration or tools are required. Downloads use the original pinned go.mod/go.sum/go.work, whose hashes must remain unchanged. GOPATH/GOMODCACHE/GOCACHE are project-scoped; GOTOOLCHAIN=local and GOENV=off. The calling shell's HOME/USERPROFILE/TEMP/TMP and inherited TDL_* remain unchanged. Binary smoke uses ProcessStartInfo with a fresh per-call storage, explicit namespace and child-only private home/temp/application-data variables, with TDL_* removed only in that child. Output stays in bounded memory; timeout and malformed/error diagnostics fail without printing raw text.

`overlay-manifest.json` hashes every reviewed overlay source. `upstream.patch` must be regenerated and checked with `git apply --check` on the pinned pristine source for each modified overlay; the build applies the equivalent overlay. `artifacts/third-party/tdl` contains the executable, exact upstream archive, complete modified source zip, license, instructions and sha256.json. Distribute the complete corresponding source/license with the matching engine. Older source ZIPs are retained. These generated files are intentionally not Git binaries. ## Exact application contract

Every invocation, including help, must have explicit `--storage type=bolt,path=<new-app-private-storage> -n <dedicated-namespace>` and private child HOME/USERPROFILE/TEMP/TMP. Clear inherited TDL_* variables. Never import old sessions. Global initialization precedes command handling; flags alone do not isolate filesystem activity. Application calls must also set `--fail-on-flood-wait`: the main client and download DC pool immediately preserve Telegram FLOOD_WAIT errors instead of sleeping/retrying. The flag defaults to false for legacy CLI compatibility. `umh login` and `umh identity` force the policy true even if explicitly passed false, so their sanitized result is `rate_limited`, not a deadline caused by hidden flood waiting. For ordinary strict list/export/download commands, raw stderr/stdout remain private; the adapter must sanitize the propagated error.

* `umh login`: code-only existing gotd auth flow, using private stdin/stdout JSONL, no Survey or QR. Authorized existing dedicated sessions emit verified account without prompting. Fresh prompts: `{ "version":1,"type":"input_required","promptId":"<48 random hex characters>","field":"phone|code|password","inputType":"text|password" }`. Phone uses text; code and password use password. Reply exactly `{ "promptId":"<active nonce>","text":"<value>" }` plus newline. No pre-sending. Maximum line 65536 UTF-8 bytes including newline; text 4096 Unicode code points, nonempty, no C0/DEL or invalid UTF-8. Duplicate keys/unknown fields/stale nonce fail. No text reflection/logging. Each command exits on cancellation/EOF/failure; login has a 10-minute deadline.
* `umh identity`: current Auth.Status and Self, no history/listing or login; two-minute deadline. Success (same for login): `{ "version":1,"type":"account","authenticated":true,"accountId":"<exact positive Int64 decimal>" }`. Optional displayName is deliberately omitted. This freshly verified ID is authoritative; stored labels are not.
* `umh chats --limit 50`: bounded chat metadata with an existing dedicated session and authorized status; no login, topics, peer resolver/cache, message content or download. Pages of 100 dialogs are read from the main list, then from the archive folder (folder 1), until `limit` chats are projected or both lists end; each next page's cursor uses the previous page's last dialog and only the date of its top message. A repeated cursor or a page whose cursor cannot be built fails. Limit defaults to50 and accepts1..5000; invalid limits fail before client creation; the command has a five-minute deadline. Version1 `type=chats` reports `limit,responseKind,chats,skippedCount,duplicateCount,truncated,completeness`; each chat has `peer_type,id,title` and optional `username`. IDs are positive Int64 decimal strings. Labels are bounded display metadata; no access hash or message content is projected. The archive entry of the main list is not counted as skipped. `responseKind` is `full` when both lists ended naturally and `slice` when the read stopped at `limit` or at a FLOOD_WAIT after the first page (which returns the chats read so far with `truncated=true` instead of failing). Only a `full` read with zero skipped/duplicate entries and no truncation is directory `complete`. Directory completeness never establishes message-history completeness. Caller-owned fresh account binding and finite output checks remain required.
* Machine failure: nonzero exit and `{ "version":1,"type":"error","code":"..." }`, with code in `invalid_input, unauthorized, auth_failed, rate_limited, network_error, cancelled, timeout, operation_failed`. No raw errors, credentials, transcript, logger or progress. Consumers still require zero exit before accepting account. `--help` is the ordinary help exception, never a login operation.
* `chat ls -o json` includes `peer_type` (`user|chat|channel`) as well as original readable `type`. Dialog dedup uses actual kind+ID; basic chat and megagroup both still have human `type=group` but different peer_type.
* `chat export --strict-peer --peer-type channel -c 123 ...` resolves **only** ResolveChannelID. Equivalent user/chat kinds are supported. Without --peer-type, `--strict-peer -c publicName` resolves the username and exports its actual kind. Strict empty/arbitrary numeric/signed/BotAPI selectors fail; unknown peer types fail. Root `{id:<exact integer>,peer_type:<actual kind>,messages:[]}` persists even for empty history. Linked discussion exports verify their actual channel class. Exported message peer must match root kind and ID.
* `download --strict-peer --restart -f <selected.json> ...`: exactly one selected file, no URLs, `--group`, or `--serve`. File schema is strict `{ "id":9007199254740993,"peer_type":"channel","messages":[{"id":7,"type":"message","file":"synthetic.jpg"}] }`. Peer ID is a **bare positive numeric Int64 token**, not a string, canonical key, negative BotAPI value, decimal or exponent. Message IDs are positive signed Int32 (MTProto message identity), exact and duplicate-free. Each message requires `type=message` and nonempty file or photo; unknown fields and duplicate keys fail. Empty selections are supported. Maximum complete input 16 MiB and 100000 messages; parse full file before any resolver call, stream message entries without float64, retain only IDs. Malformed/truncated input cannot broaden selection. One explicit resolver runs; error or returned kind/ID mismatch aborts without fallback.

Legacy ordinary login, untyped export and download CLI paths are retained for compatibility; the application MUST use the explicit strict paths. Legacy URL batching/cross-kind fallback is not repaired or accepted by strict downloads. Controller normalizes `/c/<id>` into `channel_<id>` then passes kind+bare ID; it never forwards `-100...` to a raw resolver. Application source keys and account binding stay in the adapter, not in this engine's numeric arguments.

## Validation and limits

Offline tests cover the real pipe parser through Windows OS pipes, split UTF-8, invalid/stale/cancelled/oversized input, a subprocess driving actual gotd auth.NewFlow with a synthetic FlowClient, secret suppression, exact current IDs, no-login unauthorized identity, typed resolver call counts and no fallback, selection parse limits/duplicates/range, list collisions and empty/nonempty export roots. No Telegram account/network operation is used by tests. Dependency downloads are public build inputs.

Anonymous Windows pipes may retain a synchronous reader during cancellation until their writer/process closes. Cancellation returns immediately without waiting for that OS read/close; the app's owned Job/process teardown remains mandatory. Only the process executing the cancelled operation should be terminated. Login/authentication/revocation/rate limits, actual media transfer and linked discussion behavior remain live-unverified. No claim of complete scans, successful real login, or downloaded media follows from these offline checks.

UMH.3 adds peer+message keyed dialog cursors, fatal list/topic error propagation, and a finite owned Telegram login flow with allowlisted delivery metadata and at most three explicit server-eligible resends. Each resend replaces the in-memory code hash and prompt nonce; 2FA remains in gotd. Unsupported delivery methods stop rather than showing an incorrect generic code prompt. Offline production-path regressions cover pagination collisions, terminal RPC barriers, latest-hash resend, stale/early controls, flood/cancel, unsupported methods and 2FA. No live-account success is asserted.


UMH.4 adds explicit `umh login-qr`: one initial export, buffered login-token update registered before client startup, then official pinned gotd Import (including DC migration). No automatic refresh, browser/terminal QR, session import or token file. The version 1 QR event has `pngBase64` (320px PNG, <=32768 decoded bytes) and `expiresAtUnix` (future, <=600s). Server expiry produces `qr_expired`; the overall operation remains bounded to10 minutes. A single watched nonce pipe observes EOF while waiting and accepts only the active2FA nonce. Account output still requires fresh Status/Self, with contradictory status identity rejected. The synthetic state-machine, SDK migration, transport and WPF fixtures do not establish live Telegram login.

UMH.5 adds the bounded `umh chats` metadata contract. Offline build smoke covers its help, invalid limits and unknown-flag sanitization with fresh child-only environments. Command tests must prove invalid limits return before any client initialization; these checks do not establish live directory access or completeness.

UMH.6 makes `umh chats` read the whole directory instead of one page: main list then archive folder, 100 dialogs per page, up to 5000 chats, with repeated-cursor and missing-cursor failures and a partial result on FLOOD_WAIT after the first page. Offline tests cover paging and cursor construction, the archive pass, the limit across pages, flood partials and broken cursors with synthetic pages. No live directory read is asserted.
